### S2 — Public catalog views have privileged write access

Actual database metadata confirms both `public.pod_catalog_public` and `public.pod2_catalog_public`:

- are owned by `postgres` and have no `security_invoker` option;
- are automatically updatable and insertable;
- grant INSERT, UPDATE and DELETE to both `anon` and `authenticated`;
- reference RLS-enabled tables owned by a role that bypasses RLS, without FORCE ROW LEVEL SECURITY.

The views select only published public catalog fields, which explains their intended read role. It does not justify public writes. Remove unintended write privileges and prove the intended read/tenant behavior before promotion. Avoid blindly changing the view's execution mode if that would break its deliberately public catalog projection.

This is a verified permission configuration with a strong unauthorized-write risk; no mutation/exploit was attempted. [Supabase's view/RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) explains why owner-rights views need explicit review.
