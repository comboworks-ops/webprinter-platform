# Connection repairs — 8 September 2026

Local implementation follow-up to [the connection audit](SYSTEM_CONNECTION_AUDIT_2026-09-08.md). Substantial repairs are implemented and tested. **Customer rollout remains on hold.** No linked database migration, live record change, hosted upload, payment, email, supplier submission, frontend deployment, Git staging or commit was performed.

## What changed

| Area | Local repair | Remaining boundary |
| --- | --- | --- |
| Settings | Save/Publish requires a returned tenant row. An authenticated, invoker RPC compares the settings snapshot atomically, preserves other settings and rejects conflicting writes. Drafts never become storefront publication; legacy precedence and master draft loading are corrected. | Matching migration plus real authenticated save/reload. Conflicts are rejected; stale editors are not automatically merged. |
| Payment and order | The server snapshots the checkout and approved file bytes before creating an intent. Verified Stripe completion and a signed webhook share one transactional order/file finalizer. Duplicate callbacks share one payment/order identity. Recovery and definite cancellation are retained across reload; completed checkouts restore the server receipt without creating another payment. Old deployed response formats cannot open the payment form. | New payment code defaults to disabled. Hosted Stripe and Storage testing is outstanding. |
| Server price verification | STORFORMAT uses an exact, parity-checked copy of the existing calculator with product/shop-scoped rows and required selections. Checkout retains material, finishing and product IDs plus dimensions. Matrix/fixed/rate products require one exact stored generic price. Per-area extras use verified dimensions. Existing product/extra/shipping rounding is preserved. | Fixed/rate products without stored prices still cannot quote; three such unpublished products were found in read-only inspection. Missing, ambiguous or unsupported configurations stop before an intent. Per-area frontend input now uses actual recorded format dimensions instead of an erroneous 1 m² default; the formula itself is unchanged. |
| Confirmation email | New paid completions enqueue enabled customer/operator notifications in the order transaction. A separate worker claims rows, freezes provider payloads and retries with stable idempotency keys. Test mode requires an inbox allowlist and cannot drain live-order mail. Checkout distinguishes queued from provider-accepted email. | Worker, configured sender/site origin, dedicated scheduler secret and schedule must be deployed. Delivery to real inboxes is unproven. Ambiguous results stop for review at 23 hours/eight attempts; no historical backfill occurs. |
| Manual status email | The legacy endpoint now accepts only an authenticated shop owner/operator's saved order identity. It derives recipients and content from the database, escapes HTML and uses the configured environment's site URL. Browser confirmation/new-order sending is rejected in favor of the durable queue. | Manual status/problem notifications are direct operator requests, with provider idempotency for identical payloads; they are not part of the durable confirmation queue. Their request can still be interrupted. |
| Proof approval | Approval identifies the file, SHA-256, dimensions and placement. A byte change invalidates the approved file before an intent request. Unchanged production-sized PDFs can proceed directly. Images and adjusted placements go through the existing Designer production export. Generated file hashes reach the server's immutable copies. Primary production files retain priority over alternate formats. | This is a guarded existing export route, not a new PDF renderer. Unchanged dimensions allow 0.1 mm tolerance. Professional-print-only products require a finished PDF; edits cannot bypass that rule. Designer editing remains unavailable on phones. Physical print fidelity and all multi-page exports need acceptance. |
| Replacement files | Existing undeployed finalization migration now closes the direct customer INSERT bypass. Ownership, shop, open request, expected current files, object ownership/size and replay are checked atomically. Replacement storage objects cannot be overwritten/deleted by a customer. | Requires migration and actual hosted Storage/Auth/RLS tests. Existing operator/global-admin privileges remain. |
| Messages | Customers acknowledge exact operator message IDs through a narrow RPC. Failed/partial acknowledgement does not fake read state. Restrictive policies prevent forged senders, forged read state, cross-order writes and direct customer message edits/deletes. | Hosted acceptance and notification/realtime behavior are separate. |
| Checkout addresses | Line 2 and country survive address selection, checkout persistence, profile storage and order snapshots. Delayed profile/address requests are cancelled across account changes; typed fields, including a country-only edit, survive late hydration. Address writes require a returned row. | Four additive profile columns must be deployed with the client mapping. Country input accepts two-letter codes and the existing Denmark label. |
| Designer saving | Existing saves require exact returned identity and customer/shop filters. New saves resolve the actual shop/product instead of falling back to master. Login keeps the original canvas open in its tab. Save-and-leave waits for a successful write. Single-page PDF binary data survives JSON serialization. Production exports include hashes at generation time. | Saved-design library persistence for multiple pages/sides is explicitly blocked until its document format supports those complete documents. Existing production export remains available. See the Designer repair report. |

The selected storefront/admin presets, tenant branding, core pricing calculations, POD v1/v2 pricing and supplier submission functions were preserved. The optional POD job creation and Company Hub order link run only after a durable response, using the verified order or retained checkout association. They remain browser follow-ups and can be interrupted.

Automatic confirmations now have a durable queue and dispatcher, both locally implemented. The dispatcher defaults to disabled. Provider acceptance is reported as sent; inbox delivery still needs a real test. Invoice generation, guest-order claiming, historical paid-order reconciliation and restoration of historical reorder options were not implemented. Optional POD/Company Hub follow-ups still depend on the browser.
