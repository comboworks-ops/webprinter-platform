### Original implementation sequence after design selection

1. **Keep the customer in the correct shop.** Establish one existing shop-context contract for account/auth links, signup and recovery callbacks, return targets, shop-home links and account subpages. Confirm the main Webprinter customer journey also uses the customer storefront identity. Resolve existing customer/current-shop read filtering before adding new account data surfaces.
2. **Build the selected shared account presentation.** Carry the chosen direction across overview, orders/detail, addresses, settings and auth. Preserve existing actions and routes while removing duplicated account navigation. Include empty, loading, failed and success designs from the start.
3. **Make existing actions dependable.** Finish error handling for order/detail reads, message sending/read receipts, profile/address saves and requested replacement uploads. Reconcile persisted state after each mutation; retain user input when a request fails.
4. **Complete the account-to-order bridges.** Add exact-order navigation/search, the saved-design entry and consistent profile/address use at checkout. Verify each bridge with real owned test data before claiming completion.
5. **Add only supported optional actions.** Connect eligible company access. Implement the current-price reorder proposal through existing product and checkout flows. Investigate post-order proof and invoice production as distinct follow-ups; show these only when their real availability is known.
6. **Verify the complete selected journey.** Run appropriate targeted checks and the acceptance matrix below; record browser, authenticated persistence and hosted evidence separately. Update this document with the selected direction and actual results.

### Original acceptance criteria

- Desktop (1440 px), tablet (768 px) and narrow mobile (390 px): consistent shop identity, usable navigation, readable order detail, no horizontal page overflow, reachable primary actions, visible focus, keyboard-accessible controls and clearly associated field errors.
- Signed out: storefront → login/signup → confirmation/recovery → intended account/order route retains shop context; direct account URLs, refresh and back navigation behave consistently. Check both query-context localhost and actual tenant domains separately.
- Two shops and two customers: each customer sees only the correct customer's orders/designs and the intended current-shop view. Switching shop or user clears stale rows, totals, messages and membership state before the next response arrives. Validate both denied and empty results; do not infer isolation from empty fixtures.
- First account with no orders: successful empty state gives a useful path back to shop; failed fetch never displays “no orders” as if the request succeeded.
- Returning customer: overview count matches the scoped list; a recent order opens that order; search finds the expected order; refresh preserves valid navigation state.
- Messages/files: send and reload confirms persisted content; failed send retains the draft; read receipt reflects successful persistence. Requested replacement upload handles storage failure and every subsequent write failure without a false success or lost previous current file.
- Profile/addresses/designs: save, reload and sign in again preserve intended data. Checkout receives edited contact/chosen address; saved design reopens with its original dimensions/content and correct shop context.
- Availability: tracking, invoice download and optional company access appear only when supported by retrieved data. No fabricated delivery, invoice or proof status. Reorder displays a fresh existing-system price for review.
- Evidence report records console/network failures and states explicitly which checks used UI fixtures, authenticated database-backed flows or production. No production-readiness claim follows from local visual QA alone.
